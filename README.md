# MARCO

Motor And Realtime Control Over CAN

가변저항으로 모터를 제어하고 그 명령을 CAN으로 주고받는 소형 ECU 시스템이다.
STM32F446RE의 두 CAN 컨트롤러로 게이트웨이를 구성하고(현재는 두 트랜시버를 한 버스에 묶은 시험 배선이며,
두 버스 분리는 Phase 5에서 한다),
HAL과 베어메탈의 성능 차이를 사이클 단위로 측정했다.

---

## 데이터 흐름

```
가변저항 → ADC(PC3) → CAN1이 MotorCommand 프레임 생성
   → 트랜시버1 → CAN 버스 → 트랜시버2
   → CAN2 수신·파싱 → TB6612FNG → 모터

엔코더(PA0) → TIM2 펄스 카운트 → CAN2가 MotorStatus 프레임 생성
   → 버스 → CAN1 수신 (상태 모니터링)
```

명령과 피드백이 반대 방향으로 흐르며 둘 다 실제 버스를 경유한다.
로컬에서 바로 처리하지 않은 것은 ~~센서 ECU와 액추에이터 ECU가 분리된
실제 차량 구조를 재현하기 위해서다.~~ 센서 노드와 액추에이터 노드가 나뉜 차량 구조를
한 보드의 두 CAN 컨트롤러로 흉내 내기 위해서다. 실제로는 MCU 하나, 메인 루프 하나, 버스 하나이며,
노드를 실제로 나누는 구성은 Phase 5에서 다룬다. (2026-10-25 정정)

## 측정 결과

DWT 사이클 카운터, Release 빌드, 84MHz 기준이다.

| 비교 항목 | HAL / 기존 | 베어메탈 / 개선 | 차이 |
|---|---|---|---|
| GPIO 제어 (함수 기반 HAL) | 48 cycles | 14 cycles | 3.4배 |
| PWM 듀티 설정 (매크로 기반 HAL) | 4 cycles | 5 cycles | 차이 없음 |
| 듀티 변환 (나눗셈 → Q16 양자화) | 15 cycles | 9 cycles | 1.67배, 최대 오차 ±1 |
| ADC 이동평균 필터 | 62 cycles | 83 cycles | 노이즈 표준편차 1.139 → 0.5 |

PWM에 차이가 없는 것은 `__HAL_TIM_SET_COMPARE()`가 매크로라 베어메탈과 같은 코드로
치환되기 때문이다. GPIO 오버헤드는 HAL 소스를 열어본 결과 `assert_param`이 원인이 아니었다.
`USE_FULL_ASSERT`가 비활성이면 전처리 단계에서 `((void)0U)`로 치환되기 때문이다.
남은 후보는 함수 호출과 조건 분기이며, `HAL_GPIO_WritePin`이 별도 번역 단위에 있어
LTO 없이는 인라인될 수 없다는 점에서 함수 호출 비용이 유력하다. 디스어셈블리 확인은 Phase 2.5에서 다룬다.

## CAN 메시지 설계

[`others/MARCO.dbc`](others/MARCO.dbc)에 정의했고 cantools와 CANdb++로 검증했다.

| 대역 | 버스 | 메시지 |
|---|---|---|
| 0x100 ~ 0x1FF | 제어 | EmergencyStop, MotorCommand, ControlHeartbeat |
| 0x200 ~ 0x2FF | 모니터링 | MotorStatus, PotValue, EncoderCount, DiagStatus, MonitorHeartbeat |

개발 단계에서 두 트랜시버를 한 버스에 묶은 채로 조건 없는 양방향 전달을 넣었다가,
두 컨트롤러가 서로의 프레임을 받아 다시 보내는 무한 순환을 겪었다. 받은 프레임의 ID 대역으로
소속 버스를 판별해, 상대 버스 소속 프레임은 다시 넘기지 않도록 해서 해결했다.
`EmergencyStop`의 ID가 가장 낮은 것은 아비트레이션 우선권 때문이다.

## 개발 환경

| 구분 | 내용 |
|---|---|
| 보드 | Nucleo-F446RE (Cortex-M4, 84MHz) |
| 툴체인 | arm-none-eabi-gcc (gnu-tools-for-stm32) |
| 빌드 | CMake + Ninja, STM32CubeMX 생성 코드 기반 |
| 편집기 | VSCode |
| 업로드 | STM32CubeProgrammer (ST-LINK) |
| 계측 | 로직분석기(PulseView), 멀티미터, DWT 사이클 카운터 |
| CAN 도구 | cantools, Vector CANdb++ Editor |
| 회로도 | KiCad 10 |

주변 회로는 TB6612FNG, SN65HVD230 2개, 엔코더 내장 DC 모터, 가변저항으로 구성했다.

## 진행 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| Phase 0 | 개발 환경 구축 | 완료 |
| Phase 1 | GPIO / PWM / ADC / CAN 베어메탈 전환, 엔코더 + PID 폐루프 | 완료 |
| Phase 2 | HAL vs 베어메탈, 나눗셈 vs 양자화, 원시값 vs 필터 성능 측정 | 완료 |
| Phase 2.5 | 컴파일러 관점 재분석 — 측정 하네스 보정(같은 빌드의 DWT 오버헤드 차감, 최소·최대 기록) 후 Phase 2 재측정, objdump로 최적화 확인, LTO 대조 실험, 코드 크기(Flash/RAM) 측정 | 예정 |
| Phase 2.6 | 측정 자동화 — 정적 분석, 보드 없는 단위 테스트와 커버리지 측정, 과거 결함 재주입. 커밋별 빌드와 코드 크기 기록(CI)은 Phase 3.7에서 먼저 구성 | 예정 |
| Phase 3 | CAN1↔CAN2 게이트웨이, DBC 설계, ID 대역 라우팅 | 완료 |
| Phase 3.5 | CAN 명령과 모터 제어 통합 | 완료 |
| Phase 3.7 | 결함 정리와 실패 처리 — 빌드 복구와 CI, 레지스터·클럭 설정 결함 수정, PI 제어기 구조 수정 후 CAN 통합 경로에 통합, 명령 수신 타임아웃 시 정지, bus-off 복구, 송신 실패 처리, 미구현 CAN 메시지 구현, 요구사항 목록과 운전 상태 전이표 작성 | 예정 |
| Phase 4 | FreeRTOS 이식, 인터럽트 → 큐 → 태스크 구조, 태스크 실행시간·스택 분석, 워치독과 fault 정보 캡처, 절전 코드 적용. 이어서 CAN 통신 계층 분리(AUTOSAR 통신 스택 대응, 라우팅 테이블)와 스케줄 가능성 분석 | 예정 |
| Phase 5 | 라즈베리파이 노드 결합(2채널 CAN HAT), 두 버스 물리적 분리와 게이트웨이 전달 실측(전달 수·손실·지연), 분리 후 1차 동작 영상과 PID 응답 재측정, 부하 상태의 ID별 지연 분포 | 예정 (Pi 측 환경 구축 완료, 동작 점검 미수행) |
| Phase 5.5 | MCU vs 리눅스 지연 분석 — 공통 시간축(로직분석기, 단일 시계)으로 같은 이벤트의 지연·지터를 비교 | 예정 |
| Phase 6 | HIL 테스트 — 신호 수신 타임아웃 감시(데드라인 감시) 구현 후, 장애 주입(Heartbeat 단절, 긴급정지, 비정상 명령, 태스크 정지)과 안전 상태 전환 검증(시나리오 파일 기반 자동 판정, 회귀 시험). Driver Override 구현과 전환 응답 지연 측정, 최종 동작 영상 | 예정 |
| Phase 7 | 실제 구동부 통합 데모 | 보류 |

실측 데이터와 트러블슈팅 기록은 `보고서/` 폴더에 있다.

## 현재 한계

브레드보드 프로토타입이라 전원 레일 접촉 불량, 모터와 엔코더의 GND 공유로 인한
전압 강하를 겪었다. 원인은 좁혔으나 완전히 제거하지 못했고 그 범위 안에서 검증했다.

PID 폐루프는 Phase 1-6의 단독 빌드에만 있고, CAN을 거치는 통합 경로는 가변저항 값을 듀티로 바로 쓰는
개루프다. Phase 3.7에서 액추에이터 노드가 목표 속도를 받아 폐루프를 수행하도록 통합한다.

PID 응답은 수렴 시간을 관찰로만 확인했고 원본 로그를 보존하지 못해 응답 그래프가 없다.
Phase 3.7 이후 동작 영상을 찍으면서 재측정한다.

엔코더가 1채널 펄스 방식이라 신호만으로 회전 방향을 알 수 없지만,
방향은 구동 명령으로 이미 알고 있어 속도 제어에 지장은 없다.

게이트웨이는 보드 한 장의 CAN1/CAN2로 구성했다. 분리된 두 버스에 별도 노드를 붙이는
구성과 다중 노드 아비트레이션 실측은 Phase 5로, HIL 테스트는 Phase 6으로 미뤘다.

현재 배선은 두 트랜시버를 같은 버스에 묶은 상태다. 그래서 한쪽이 보낸 프레임은
물리 버스로 반대편 컨트롤러에 직접 도달하고, 게이트웨이의 전달 코드는 실행되지 않는다. 각 컨트롤러가
받는 프레임이 모두 상대 버스 대역이라 전달 조건이 거짓이 되기 때문이다(코드 추적 기준). Phase 3.7에서
전달 분기 실행 횟수를 세는 카운터로 이를 실측 확인하고, 실제 전달은 두 버스를 분리하는 Phase 5에서 검증한다.
초기 문서는 이 구조를 "CAN 컨트롤러가 자기 송신을 다시 수신한다"는 잘못된 전제로 설명했고,
RM0390과 대조해 정정했다.

CAN 송신은 메일박스 하나만 쓰고, 비어 있지 않으면 프레임을 기록 없이 건너뛴다. 게이트웨이 전달도 같아서
반대편이 바쁘면 전달 프레임이 사라진다. 손실을 세지 않아 실제 손실 여부는 확인하지 않았다.
Phase 4에서 송신이 결과를 반환하고 손실 횟수를 진단 메시지로 보고하도록 바꾼다.

Phase 2에서 양자화 방식이 1.67배 빠르다고 측정했으나 Phase 3 운용 경로는 아직 나눗셈 함수를
쓰고 있다. MotorStatus의 방향 필드도 상수로 고정되어 있다. 둘 다 Phase 3.7에서 정리한다.

GPIO 오버헤드의 원인은 HAL 소스 분석까지만 확인했고 디스어셈블리 레벨에서는
검증하지 않았다. 이 부분은 Phase 2.5에서 objdump 확인과 LTO 대조 빌드로 다룬다.

성능 측정은 실행 사이클이라는 단일 축으로만 이뤄졌다. Flash와 RAM 사용량은 아직 측정하지 않았고 Phase 2.5에서 다룬다. 태스크별 스택 사용량은 단일 루프 구조인 현재는 결정할 일이 없어 Phase 4로 미뤘다.

코드 크기는 Phase 2.5에서 다루고,
전력 소비는 측정 지표에서 제외했다. 측정 모듈 자체는 저렴하지만, MCU만 정밀하게 재려면 션트 저항 교체와
캘리브레이션, 측정 지점 배선이 필요하다. 자동차 제어 영역에서 전력이 실시간성보다 우선순위가 낮다는 점과
투입 대비 산출을 함께 고려한 판단이다. 절전 코드는 Phase 4에서 적용하되 절감량을 측정하지 않으므로
최적화 성과로 서술하지 않는다.

측정은 특정 시점에 손으로 수행한 스냅샷이라, 이후 커밋에서 코드가 커지거나 느려져도
드러나지 않는다. 커밋별 자동 추적은 Phase 2.6에서 다룬다.

검증은 전부 실보드에서 수동으로 이뤄졌고, 보드 없이 실행할 수 있는 테스트가 없다.
하드웨어와 분리한 로직(신호 패킹, 라우팅 테이블, 듀티 변환, 운전 상태 전이)의 단위 테스트는 Phase 4의 계층 분리 이후
Phase 2.6에서 다루고, 장애 주입 시나리오는 Phase 6에서 가상 CAN으로 먼저 검증한다.

라즈베리파이 노드가 OS 스케줄러 때문에 정확한 주기를 보장하지 못한다는 점은 아직 추정이다.
MCU와 리눅스의 지연·지터를 같은 프레임으로 비교하는 실측은 Phase 5.5에서 다룬다.

시간 특성은 개별 함수의 실행 사이클까지만 확인했고, 여러 주기 작업이 함께 도는 상황에서
마감을 지키는지는 검증하지 않았다. 현재 구조가 단일 루프라 애초에 검증 대상이 아니며,
태스크 단위로 나뉘는 Phase 4에서 다룬다.

인터럽트 핸들러가 UART 출력과 모터 제어를 직접 수행하고 있다. 블로킹 전송이라 핸들러가 오래 점유되고
재진입 시 출력이 섞일 수 있어, 인터럽트는 짧게 유지한다는 원칙에 어긋난다. 30자 안팎을 출력하면 핸들러가
약 2.6ms 점유되는데 CAN 수신 FIFO는 3단이라, 버스 부하가 있으면 수신 오버런이 날 수 있다. 디버깅 편의를 위해
현재는 유지하고 있으며, 태스크 구조로 바뀌는 Phase 4에서 인터럽트는 큐에 넣기만 하도록 분리한다.
같은 핸들러에 ID 판별·재전송·신호 파싱·모터 제어가 섞여 있는 구조도 이때 드라이버 / 라우팅 / 신호 / 응용
계층으로 나누고, 게이트웨이 판별을 라우팅 테이블로 바꾼다.

DBC에 정의했으나 송신 코드가 없는 메시지가 있다. EmergencyStop, PotValue, EncoderCount,
DiagStatus가 해당하며, 이 중 둘은 수신 파싱만 구현되어 있어 해당 분기가 실행되지 않는다.
잔여 결함 정리와 함께 Phase 3.7에서 다룬다.
